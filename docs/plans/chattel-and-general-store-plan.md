# Chattel possession core + the general store — implementation plan

A property-first cycle: land the **chattel possession core** (per-instance ownership of goods — the twin of the shipped parcel title) and prove it with the first **retailer** business, a **general store**. The store rides *real* ownership; its consignment loop (custody-vs-ownership) is the proving consumer that forces the ownership design honest. One cycle, **two MRs** at the substrate↔consumer seam. Read `docs/requirements/chattel-and-general-store-requirements.md` in full before starting; it is authoritative.

The chattel core is the [property slate](../slates/builds/property-slate.md)'s Phase-0 possession core (chattel half) — the **minimal ownership slice**: the owner-stamp, `ownerOf(item)`, first-class `transfer`, and a durable per-instance identity. The property compute/economy (cost-owner, the `Charge`-debtor gap, allowance) stays deferred. The store side reuses the substrate grounding already established (banking splits, `ResidencyLogic`, `Menu`, Attendant, employment), revised so `buy` stamps the buyer and consignment is modeled as custody-vs-ownership.

## Grounding (facts established by investigation)

### The crux — the durable per-instance id (resolved: mint on first stamp)

1. **No durable per-instance id exists today; inventory is re-cloned on restore.** The spine captures a plain (non-host) inventory item as `{ templatePath, state, placement }` (`obj/api/PersistableLogic.ts:295-301`, `captureItem`), and restores it by **cloning a fresh instance from `templatePath`** (`:405-414`, `restoreItem` → `StuffApi.clone(entry.templatePath)`). The clone gets a **new `stuffId`** (runtime-only, regenerated every clone/hydrate — the same field residency's `lastTouched` resets on). So a torch you own, logged out and back, is a *different* instance with no identity linking it to the old one.

2. **Neither shipped identity field can key ownership.** `stuffId` is runtime (not persisted, re-minted per clone). `templatePath` is *shared across all clones of a template* (`/obj/Torch` is every torch) — it cannot distinguish two torches, and cannot carry per-instance ownership. `authorOf` (`api/provenance.ts:107`) keys on a **path**, not an instance — it is the right *fallback* (author of the template) but cannot express "this particular torch is yours."

3. **Only Persistable *hosts* get their own record; a torch is absorbed, not keyed.** A `PersistedRecord` is `(scope=templatePath, key=owner)` and exists only for hosts that compose `Persistable` (Avatar, titled rooms, chests — `PersistableLogic.ts:106-134`, `441-468`). An inventory item is captured *inside* the host's Container slice, not as its own keyed record — so it has no independent persistence identity to reuse.

4. **Recommendation (b) — the chattel core mints a durable id on first stamp, persisted as a declared field on the item, and keys the registry on it.** A declared persistent field **does** survive the round-trip: `captureState` walks `getPersistenceContributors` and captures each layer's declared persistent fields (`:256-287`), and `restoreState` re-hydrates them, drift-guarded to `getAllPersistentFields` (`:319-344`). So a `_chattelId` field, minted server-side on first stamp and declared persistent, rides the avatar-inventory (and the shop-container) round-trip intact, and the `chattel` registry row (id→owner, in Mongo) is independently durable. Ownership = registry-row-keyed-by-id; the item carries only its *identity* (not its owner — the owner stays an unspoofable registry fact). **This is the #1 risk** (see below): id uniqueness, the gated write of `_chattelId`, and the blast radius of the field's host tier.

4a. **The stamp is discrete-only; fungible stacks stay owned-by-possession (grounded).** A `_chattelId` is coherent only on a **discrete** Stuff. `Globbable` is structurally incompatible: a glob is one Stuff carrying `quantity` that **splits into siblings sharing `templatePath`** (`lib/stuff/Globbable.ts:135-174`) — a split of a stack of 5 has no answer for which unit keeps the id — and **merges when every `globIdentityFields` value is equal** (`:194-219`); a per-instance id would either collide on merge or (if added to `globIdentityFields`) make two owned stacks refuse to merge. `Globbable ⊥ Container` and `⊥ Singleton` are already enforced (`:147-161`). Coins and `Bandage` are the shipped globs (`obj/Coin.ts`, `obj/Bandage.ts`). So chattel ownership is **scoped to discrete goods**; fungible stacks stay **owned-by-possession** (whoever holds them), carry no stamp, and `ownerOf` on a glob is not asked. Coin ownership was never a chattel concern — coin *is* the money substrate, conserved by the banking ledger, not the ownership registry.

4b. **Ownership survives a relog only for a good held by a `Persistable` host — call it out.** The `_chattelId` rides the round-trip only because some host captures the item into its record (Avatar inventory, a persistable chest, or the P4 consignment shelf). A discrete good **dropped in a plain transient room** is not captured by anything — the room itself culls and re-clones from template (residency), so the item is simply **gone** on relog, and its ownership is moot (there's no instance to own). This is consistent and acceptable — you don't persist litter — but it makes the **consignment shelf being `Persistable` load-bearing, not incidental**: a consigned player-owned good sits in the shop's custody across a relog *only because* the shelf composes `Persistable` (P4) and captures the item + its `_chattelId`. If the shelf were a plain transient container, a consigned item would vanish on a server bounce and the consignor's ownership row would dangle (until the GC/reconcile path clears it).

### The parcel trio to mirror

5. **The chattel trio is a structural clone of the parcel trio.** `ParcelApi` (thin facade, `api/parcel.ts`) → `ParcelLogic` (`/obj/api/parcel`, registry-resolution + a **pure degrade** when no registry, `obj/api/ParcelLogic.ts:53-63`) → `ParcelRegistry` singleton (`/obj/ParcelRegistry`, the index + mutators, every method `@CallSecurity(AnyOf(FromModule('/api/parcel#ParcelApi'), FromTemplate('/obj/api/parcel')))`). State lives in two collections: `parcels` (rebuildable current-state `ParcelRecord extends Document`, `lib/parcel/ParcelRecord.ts`) + `parcel_events` (append-only chain-of-title; a `transfer` *appends*, never overwrites — `ParcelApi.transfer` doc, `parcel.ts:104-114`). Ownership stored **separately from the editable content it gates** — the governing security invariant (`ParcelRecord.ts` class doc). Chattel is the sibling: `ChattelApi`/`ChattelLogic`/`ChattelRegistry`, `chattel`/`chattel_events`, keyed on the durable **instance id** (not a path), resolved `stamp ?? authorOf`.

6. **`ownerOf` is a total resolution chain; chattel's is two-rung.** `ParcelApi.ownerOf(path)` = title → self-home → state-`core`, total (`ParcelLogic.ts:53-63`). Chattel's `ownerOf(item)` = **stamp (registry row on the item's `_chattelId`) → `ProvenanceApi.authorOf(item.getTemplatePath())`** — so an unstamped content item resolves cleanly to its author, no world-wide restamp (requirements Goal 2). `ProvenanceApi.authorOf` is already gated-clean and derives the earliest authoring row (`provenance.ts:102-109`).

### The store-side substrate (carried from the prior grounding, revised for the stamp)

7. **`settle` + `Charge.splits` afford the consignment split unchanged.** `Charge.splits` routes cuts to third-party accounts alongside the main leg (`lib/banking/Charge.ts:24-49`), posted for both credential and cash paths (`obj/api/BankingLogic.ts:573-663`) through the sealed `postTransaction` (`:857-894`); the split total is validated ≤ the charge (`:639-642`, `:574-576`) so commission + remainder must sum to the ask — conservation by construction. Consignment tax = `remitDemoTax(storeAccount, commissionMoney)` (commission is the store's taxable revenue, `:720-738`). **Offline payout is safe**: `primaryAccountIdOf(ownerKey)` is a pure DB read (`:1108-1113`).

8. **The buy side is the bar's order→Charge hook, plus a stamp.** `OrderController.charge` (`obj/command/crafting/OrderController.ts:130-173`) is the template (ensure Business/venue account, presented `Charge` `category:'sales'`, `settle` credential→cash fallback `:161-168`, `remitDemoTax`). `buy` mirrors it, then hands over the item **and calls `ChattelApi.stamp(item, buyer)`**.

9. **Employment/Attendant/reset findings unchanged.** The store `Business` P&L "just works": `settleShiftWageImpl` keys the employer account on the Business path and **auto-provisions an NPC clerk's account** (`obj/api/EmploymentLogic.ts:176-181`); the roster tick runs on the **game-time** clock (`WorldClockApi.every`, `:301-313`). Attendant scrum/instant is a behavioral no-op the bar already proves (`lib/attendant/Attendant.ts:206-210`; `bar-counter.yaml`). The reset sweep's sibling seam is reserved in `ResidencyLogic` (`obj/api/ResidencyLogic.ts:184-206`) with `presenceWalkImpl` reusable (`:74-88`); `residency.reset.*` is anticipated in `AppSettingKeys` (`lib/config/AppSettings.ts:349-360`). The reset predicate differs from eviction's idle+`canEvict` (presence-skip + object override, no idle threshold) — structural mirror, not literal.

10. **The shared offer extraction must preserve `Menu`'s field names for parity.** `Menu` persists `offeredRecipes` + `prices`, exposes `priceFor` (`domain/lounge/Menu.ts:29,84-98`); bar seeds/tests use those names. Extract only the **price-list** (`prices` + `priceFor`) into a mixin — the genuinely shared thing — so `Menu`'s field/signature survive verbatim.

11. **`Branded` gives independent shelf marks; the store Business carries no corpoKey.** `BrandedMixin` resolves an empty-owner brand to a null corpo — "an independent label" (`lib/corpo/Branded.ts:82-85,120-130`); corpoKey lives on fixtures, never the Business (`lounge/business.yaml`). Franchising is S4.

## Phase sequencing

**MR #1 (substrate):** **P0** chattel possession core — the trio, `chattel`/`chattel_events`, the durable-id mechanism, `ownerOf`/`stamp`/`transfer`, the author fallback, boot wiring, and a demo/test vehicle proving ownership survives a container move + persistence round-trip *independent of the shop*.

**MR #2 (consumer):** **P1** offer-extraction + bar parity → **P2** store as `Business` + Attendant + buy-that-stamps → **P3** reset-sweep substrate + shop stock consumer → **P4** consignment on the stamp + the per-consignor cap → **P5** store content near the Terminus new-player path → **P6** finalize-doc prep.

Dependency order: P0 stands alone and merges first (the foundation many builds want); every P2–P4 ownership touch calls the P0 Api. Within MR #2, P1 is a clean baseline, P2 needs P1's offer, P3's consumer needs P2's store, P4 extends P2's buy surface onto P0's stamp, P5 wires it into content, P6 is docs.

**Steps.**

Compose it at the **movable-good tier** — recommend `Thing`/`Tangible` (generality: pets/apartments/ranching/retail-S4 all want per-instance identity), flagged for sign-off; the narrower alternative is composing only on the store's good classes + the demo class.
- Add the trio:
  - `obj/ChattelRegistry.ts` — singleton at `/obj/ChattelRegistry`, an in-memory `Map<chattelId, ChattelOwner>` index over the `chattel` collection; methods `ownerOf(id)`, `stamp(id, owner)`, `transfer(id, newOwner)` (append `ChattelEvent` + upsert `ChattelRecord` + update index), `newId()` (collision-resistant, e.g. nanoid), all `@CallSecurity(AnyOf(FromModule('/api/chattel#ChattelApi'), FromTemplate('/obj/api/chattel')))`.
  - `obj/api/ChattelLogic.ts` — `extends ApiLogic`, registry-resolution + the **pure degrade** (no registry / no row → author fallback), the `ParcelLogic` shape. `ownerOf(item)`: `id = item.getChattelId(); if (id && reg.ownerOf(id)) return that; else return authorOwner(await ProvenanceApi.authorOf(item.getTemplatePath()))`. `stamp(item, owner)`: ensure `_chattelId` (mint via `reg.newId()` + gated `_setChattelId` if empty), then `reg.stamp(id, owner)`; actor from `ExecutionContextApi.getActingAuthor`. `transfer(item, newOwner)`: ensure id, `reg.transfer`. `@CallSecurity(FromModule('/api/chattel#ChattelApi'))` on each. `stamp`/`transfer`/`ownerOf` **refuse a `Globbable`**: `ChattelLogic` guards each entry with `MixinApi.isGlobbable(item)` and, on a glob, returns a clear no-op (`{ ok:false, reason:'fungible stacks are owned by possession, not stamped' }`) rather than minting an id it can't keep stable across split/merge — the structural enforcement of the discrete-only scope, not a soft convention (a P0 test asserts stamping a coin stack refuses).
  - `api/chattel.ts` — `ChattelApi` thin facade forwarding via `StuffApi.singletonSync`, ending `SecurityApi.decorateApiClass`. Public: `ownerOf(item)`, `stamp(item, owner)`, `transfer(item, newOwner)`. The actor is always context-derived.
- **Registry GC on destruct (no leaked rows).** A stamped discrete good that is destroyed (residency cull, consumption, `StuffApi.destruct`) must release its `chattel` current-state row, or every consumed torch leaks a row forever. Add the cleanup to `ChattelMixin` via the terminal `onDestruct()` witness (`Stuff.ts:811-825`; chain `super.onDestruct()`): if `getChattelId()` is set, call a gated **`ChattelApi.release(item)`** → `ChattelLogic` removes the current-state `chattel` row for that id and clears the `_chattelId` (via the same gated `_setChattelId('')` seam), while **appending a terminal `released` event to `chattel_events`** (history is never overwritten). This **diverges from the parcel side deliberately**: parcel `retire` is a hard row delete with no event (`ParcelRegistry.ts:287-288`) because a retired dorm slot is administrative churn, whereas a destroyed good's chain-of-title should terminate legibly — so chattel keeps the terminal event `retire` omits. Add `ChattelApi.release` to the facade, gated like `stamp`/`transfer`; actor context-derived. Verify: a stamped item destructed leaves no `chattel` row, a terminal `chattel_events` row, and a fresh unrelated clone's `ownerOf` is unaffected.

**Reuses.** The parcel trio homes/gates (`api/parcel.ts`, `obj/api/ParcelLogic.ts`, `obj/ParcelRegistry.ts`), `ProvenanceApi.authorOf` (`provenance.ts:102-109`), the spine's declared-persistent-field capture/restore (`PersistableLogic.ts:256-344`), `Document`/collection machinery, `ExecutionContextApi.getActingAuthor`.

## Resolved decisions (closed by the requirements)

- **Property-first, one cycle, two MRs** (option B), split at the substrate↔consumer seam. MR #1 = the chattel core; MR #2 = the store as its proving consumer.
- **Ownership is a gated registry fact, not a mixin field** — `ChattelRegistry`/`chattel` keyed on a durable instance id, resolved `stamp ?? authorOf`. **No `Ownable` mixin, no owner field on the item.** The `_chattelId` is *identity* (server-minted, gated-write), not authority.
- **Chattel = discrete goods only; fungible stacks stay owned-by-possession.** The `_chattelId` stamp is coherent only on a discrete instance; a `Globbable` stack (split/merge) cannot carry a stable per-instance id (`Globbable.ts:135-219`). So ownership is scoped to discrete Things; fungible stacks (coins, and any glob) are owned by whoever holds them, unstamped. Consequences: the store's ownable staples **must be discrete Things** (P5 content constraint); `ChattelApi.stamp`/`transfer` **refuse a `Globbable`** (P0); **consignment is discrete-goods-only in v1** (matching the stamp scope — you cannot consign a fungible stack). Fungible-goods retail (selling/consigning stacks) is deferred with the broader glob-ownership question.
- **Minimal chattel slice** — owner-stamp + `ownerOf` + `transfer` (+ the store consuming it). Deferred: the compute/economy (cost-owner, the `Charge`-debtor gap, allowance), and a general `give`/trade/dispute surface (the `transfer` primitive makes it a thin later add).
- **Custody-vs-ownership consignment** — `consign` moves custody, the stamp stays; the sale transfers custody **and** the stamp; `reclaim` returns custody (ownership never left). The listing is a brokerage record, not an ownership pointer.
- **Carried store decisions** — buy + consignment both in; payout → the consignor's primary bank account, account required to consign; per-consignor listing cap; reliably-available stock via the reset sweep (shop `reset()` overrides the presence-skip); independent store; instant/scrum staffed counter; sales tax reuses `remitDemoTax` (consignment tax = commission); prices authored as stance; the bar refactor in-scope with parity a hard constraint; conservation/Law 1/Law 2 respected.

## Highest-risk spots (verify hard)

- **#1 — The durable per-instance id (P0).** The load-bearing decision. Verify: (a) `_chattelId` genuinely survives the avatar-inventory capture/restore round-trip (it must be a *declared persistent field* on the item's mixin so the drift-guarded hydrate re-applies it, `PersistableLogic.ts:319-344`); (b) it survives while in the **shop's** custody (the consignment shelf must be a `Persistable` host so its Container slice captures the item + id); (c) id **uniqueness** — mint via a collision-resistant generator, the mint path (ChattelLogic) is the sole writer, templates seed empty, and no capture/restore path duplicates an id onto two clones; (d) the `_setChattelId` write is gated to the chattel logic (a player/author cannot forge identity); and (e) **no leaked rows** — a destructed stamped good must release its `chattel` current-state row via the `onDestruct` witness (the Phase 0 GC step), keeping only a terminal `chattel_events` entry; a residency cull of an owned item that skips release would strand its ownership row and (worse) let a future clone that happens to re-mint the same id inherit a stale owner — so verify the GC fires on the residency `destruct` path, not only explicit `StuffApi.destruct`.
