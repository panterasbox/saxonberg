# SmeltController — packages/content/trade-smelting/src/idea/cmd/smelting/SmeltController.ts (1,035 lines)
**What the command is:** `smelt [at <furnace>]` runs whatever is in a furnace (ore or bar + charcoal ± flux) for 2 game minutes and taps out metal, cast iron, steel, bloom or slag, decided by chemistry.
**Verdict:** about 75% game rule, 10% presentation, 10% coordination, 4% parsing/routing, 1–2% unclear. This file is the smelting simulation. The verb is wrapped around the outside of it, and the furnace class that affords the verb (`src/thing/SmeltingFurnace.ts`, 40 lines) holds none of it.

**What a player rewriting it would be forced to copy today:**
- The whole Fe–C model (≈20 constants, `meltingPointOf`, `carbonFor`, `ferrousMaterialFor`). If they leave it out, steel stops existing.
- Charge classification and the five predicates, plus the three refusal rules (no ore, mixed charge, under 16 kg of fuel).
- The run's duration and effort, and building the `ManualBuildStep` themselves.
- `runCharge` in full: consumption, mass sums, slag pours, lining wear, crucible run, crucible wear and crack, trapped-slag mass, carbon stamping, product-row search, the deed outcome table. The only part they want is `tapScene`.
- The trap that the completion must be a module function because the controller is destructed before the run ends (351–357, 407–409).
- The `isClamp` duck-type, because otherwise the clamp next door binds.

**Hard cases (unclear) and the question each raises for a rule:**
1. **Too-cold advice (316–345).** "Work the bellows" or "this fuel doesn't burn hot enough" picks a cause by reading `isLit`, `isBellowsActive` and `held` against `wanted`. Is the cause a world fact, so the furnace returns `{reason: 'unlit' | 'needs-draught' | 'fuel-ceiling', heldK, wantedK}`, or is it advice and therefore presentation? Question: must a refusal carry enough structure that a rewrite can word it differently without re-reading the object's state?
2. **Deed outcome (504–510, 578–590).** Steel is `hard`, cast iron and soured iron are `partial`, copper is `success`. That is advancement policy grounded in "not the metal you meant", which infers an intent the verb deliberately never takes. Question: is the deed's grading part of the act's result (the object's), or the controller's verdict on the player? If a rewrite changes it, the transcript changes, which suggests the object.
3. **Which vessel catches the melt (791–805).** "The first crucible; a furnace has one, so nothing is chosen." If two crucibles stand in a furnace, prompting for one would be a question of asking (presentation), but the code treats it as a world fact. Question: when an object holds several candidate targets, is picking among them a binder/prompt concern or the object's rule?
4. **Clamp decline (238–245).** If the view bound only things that afford `smelt`, a player at a clamp would get the binder's generic "nothing to smelt" and lose the teaching sentence ("a clamp keeps the air OUT"). Question: where does "this isn't the right kind of thing, and here's why" live once routing stops letting the wrong object through: on the object, in the view's no-match text, or nowhere?

**Rules this controller suggests:**
1. **What outlives the controller isn't the controller's.** If a completion has to be written as a free function because the controller is destructed before it runs, that code belongs to the object that persists through the act. Test: does any code run after `execute` returns? Evidence: 351–360, 407–409. `runCharge` and its helpers are about 600 lines that already left the class, but they landed in the same file.
2. **A number that changes the world is never in a controller.** Test: would changing the constant change what happens rather than what is said? If so, it is the object's or the material's. Evidence: 72–176 (durations, effort, minimum fuel, the Fe–C phase diagram).
3. **The object returns a reason; the controller words it.** Refusals and outcomes come back as structured results (code + the numbers), and the controller only chooses sentences. Test: can a rewrite produce every message without calling any getter on the world? Evidence: 260–345 and `tapScene`'s nine positional arguments (594–604), which are a result object waiting to be named.
4. **A verb binds what affords it.** When a class declares the view in `commandContributions`, the binder's default resolves to afforders, and the controller does not re-narrow or sniff other packs. Test: does the controller re-check a mixin or class the view could have declared? Evidence: 220–245, 961–966, against `SmeltingFurnace.commandContributions` and the view's `default: "reachable:[mixin.BurnerMixin]"`.
