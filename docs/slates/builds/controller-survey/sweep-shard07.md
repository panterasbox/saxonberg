**Hard cases**:
- WorkedActController 97-100 (`boundIsWorked`): a heuristic that decides whether the player's word names the thing or a band in it. Is "what did the player mean by this word" binder work or presentation? Rule question: may a controller reinterpret a successful bind?
- DigController `subjectOf` ladder: the room/floor fallback is "which thing the act is about", a world fact, but expressed as scope. Should a view's `default:` be allowed to be an ordered ladder of scopes?
- EquipControllerBase `dressNext`: the layer-depth sort is presentation-adjacent (ordering) but a different order changes what ends up worn. Is "order of a batch" a rule when order changes the outcome? I'd say yes.
- Drop's fall (`landDrop`): is "drop means it falls" the verb's meaning (controller) or the move's physics (object)? `put` deliberately doesn't fall. Suggests a move *mode* on ContainmentApi.
- Cover vs `draught banked`: same state change, different sentence. Is that two controllers or one view alias with a wording option?

**Rules** (new):
- (12) A dial (`AppApi.setting`) read in a controller is a game rule: tuning knobs belong to the object that obeys them. Evidence: Cover 31-40, Disarm 189-198, Drop 274-283, EquipBase 143-152/513.
- (13) A word→number table shared by two verbs is a vocabulary row on the object. Evidence: Draught `NAMED` 48-54 copied as Fire `DRAUGHTS` 55-61.
- (14) A controller that self-dispatches on `model.subcommand` when the view could name a per-subcommand `controller:` is parsing in the wrong place. Evidence: Office 45-52 vs equip.yaml's `set`/`sets`.
- (15) A catch-all `catch` that changes WHICH act happens (not just how it's worded) is a game rule. Evidence: Tip 77-79.
- (16) When the object already has `xRefusal()`, any extra refusal in the controller is a gap in that method. Evidence: Fold 74 vs 88-107.
