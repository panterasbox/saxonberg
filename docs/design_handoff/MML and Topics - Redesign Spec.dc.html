MML and topics, redesigned around the client

Both vocabularies grew from server-side need, one emitter at a time. This proposes what they should be if the question were what does a person using the web client need — and specifies the server changes that get us there.

1 · What went wrong, precisely

Nothing here was a mistake at the time. Client support was built to test server behaviour, so both vocabularies record what the server emits rather than what a person attends to. Three consequences, each visible in the current tree.

Pathology 1 — one topic per emitting code path

There are 13 system.shell.* topics — fs, var, alias, group, contacts, settings… Those are the shell's command categories, not classes of attention. Nobody mutes shell.fs but not shell.var.

Likewise world.perception.measurement.* is 15 topics — one per verb × channel (measure-temperature, analyze-chemistry, weigh…). The dotted path is doing the job of a function name.

Pathology 2 — the client must hardcode topic strings to decide anything

The wire carries {topic, family, label, description}. None of those say whether a frame is addressed to me, whether it matters, or whether it should interrupt. So every filter tab, mute rule, badge and notification threshold becomes a client-side lookup table keyed on 89 topic strings, drifting silently from the seeds. The knowledge lives in the wrong repository.

Pathology 3 — the differentiator is untagged

The taxonomy devotes 15 topics to measurement. The MML vocabulary — all 32 tags in KNOWN_TAGS — has no tag for a measured value. A temperature is routed as a measurement and then rendered as prose: 1240 °C arrives as characters.

The client therefore cannot convert units, compare against a working range, pin a value to an instrument panel, chart it over time, or feed the analyze view — without re-parsing strings it should never have had to parse. Real quantities are what this game has that no other text world has, and the markup drops them at the last inch.

2 · Two vocabularies, two questions

The pair has been treated as one metadata system. They answer different questions at different scopes, and designing each against its own question is most of the fix.

3 · Topics: reshape the tree, then add facets

Why renaming is the work, not a nice-to-have. The dotted path is not an internal identifier. family drives grouping and gutter colour, and prefix subtrees are the only way to mute a class of thing as a unit. Tree shape is UI shape. Facets (below) fix cross-cutting queries — everything addressed to me — but only the tree fixes subtree mutes — everything about the air in here. Both halves are needed, and the rename cost is at its lifetime minimum today.

3.2 The facets

A reshaped tree still expresses only one hierarchy. These five fields carry the cross-cutting questions the client asks on every frame, so the answers live in the seeds instead of a client lookup table.

Five facets across ~60 topics is not 300 hand decisions: audience and actor derive mechanically from the family prefix. A script sets defaults; review touches only exceptions.

4.1 The addition that matters: <measure>

One tag closes Pathology 3. The server already knows every one of these fields at compose time — it computed them.

<measure channel="thermal" value="1240" unit="degC"
         via="pyrometer" lo="1150" hi="1300">1240 °C</measure>
Attribute Why the client needs it
channelStable identity for pinning to an instrument panel and charting a series. Same vocabulary as world.measure.<channel>.
value + unitCanonical numeric and unit code. Enables conversion (°C ↔ °F), comparison, sorting, and tabular figures in the type.
viaProvenance — which instrument produced it. This is the pedagogical seam: a reading is only honest if you can say how it was taken.
lo / hiOptional working range, so “in window” styling is declared by the server rather than hardcoded per craft in the client.
childrenThe server's own rendering, so flatten yields correct prose and a bare telnet client still reads “1240 °C”.
Security: <measure> must never be inert

By the reasoning already written into INERT_TAGS: it is a factual claim about the world on the server's authority, exactly like speech. A player who could type it into chat could forge instrument data — worse than misattributing words, because the whole premise is that the numbers are real. It belongs in KNOWN_TAGS only, with a flatten entry, and stays out of every passthrough policy.

4.2 Lower-priority additions

<skill> — skill references are central to advancement and currently render as bare words; a tag would afford “show my rank, show practice history.” <coin> or <measure unit="coin"> for money, once the currency work settles. Both are worth doing after <measure> proves the pattern; neither is urgent.

On step 5. The seed descriptions are written for server developers — “Dynamic per-level leaves (info, warn) inherit from this family,” “Output of workspace filesystem verbs — pwd, cd, ls, cat…”. They are also the only human-readable strings on the wire, so any filter UI the client builds inherits that voice. Whatever a player reads in a mute list should be written for a player.

Open questions for the server side

  1. Is the item / object split portable-versus-fixed, or historical? The answer decides keep-or-collapse.
  2. What is msg for, distinct from speech and chan?
  3. Should communicative join the facets and go on the wire? It is currently server-only, so the client cannot show why an utterance earned renown.
  4. Does the measurement channel list (thermal, light, atmosphere, chemistry, electrical, mass, position, weather) match the engine's own channel enum? They should be the same list in one place.

6 · The authoring vocabulary

§4 judged each tag against one question — does the client afford it differently. That is the right question for the client and the wrong one for the person writing the world. This section supplies the missing axis, and in doing so resolves the three verdicts §4 left open.

The tension. The client rule minimises the vocabulary: collapse anything that affords the same. The authoring requirement maximises it: someone writing a limestone cavern and someone writing an orbital habitat need to say different things. Applied alone, the first yields a vocabulary too thin to write in; the second yields hundreds of tags the client cannot act on. Today's 32 tags attempt both on one axis, which is why item versus object is unresolvable — it is an authorial distinction wearing the costume of an affordance.

6.1 Closed tags × open attributes

They are two axes, and separating them dissolves the conflict rather than trading it off.

This is how HTML solved the identical problem: a closed element set with an open class vocabulary. The author's range is unbounded; the client's stays fixed. The net is fewer tags and more expressive power — 28 rather than 32, because expressiveness moved off the tag and onto an attribute that can grow without a release. §6.3 identifies what that attribute should be, and the answer is that it already exists.

6.2 The closed set

Class Tags Behaviour
Affordance-bearing player · npc · thing · place · exit · detail Carry a stuff-id. Clickable, and open a context menu.
Informational measure · sense · speech Styling and inline widgets — a unit toggle on a measure — but issue no command.
Reference link · chan · mention Already command carriers with their own semantics.

Resolving §4's three open verdicts:

  • item + object → collapse to thing. The distinction people reach for is portability, and portability is not a kind — it is state. A sword on a table can be taken; the same sword bolted to a wall cannot. Same tag, same kind, different answer at different moments, so it can only come from the live resolve in §6.4.
  • name → retire. With player and npc both kept, it has no remaining role.
  • player / npc → stay two tags. An account behind the character is a different menu, not a different flavour.

6.3 The vocabulary already exists: mixins

An earlier draft of this section proposed a kind registry. That was a mistake: it would have been a second taxonomy describing what a first taxonomy already knows, and the two would have drifted the first time an author composed a mixin without updating a kind. The ~180 entries in lib/mixin.ts are already authored, already introspectable at runtime through MixinApi.hasMixin, and — decisively — already affordance-shaped.

A menu is the union of what an object's composed mixins confer. Composition also answers the inheritance question a kind registry would have raised: an anvil is Tangible + Tool + Durable + Fixture, and that is its affordance set — no parent chain to maintain, because the object already declares its parts.

The one thing to add is where each mixin says what it confers. A static beside fieldMeta, collected up the prototype chain exactly as getAllFieldMeta already does:

// SealableMixin
static affords: Affords = {
  open:  { category: 'manipulation', when: 'closed' },
  close: { category: 'manipulation', when: 'open' },
};
The pedagogical dividend

If the client names the mixins, playing the game teaches the authoring palette. It is the same thesis as clicks-teach-the-command-line, one layer up: point at a lamppost, see Switchable · LightSource · Fixture, and follow any of the three to its wiki page. By the time someone opens the Studio the vocabulary is already familiar — and because they met it on real objects, they know what each part does, not just what it is called.

A kind registry would have taught players a vocabulary that exists nowhere else in the system. Mixins are the real one.

What is left for genre flavour. Mixins cannot distinguish a rune-stone from a plasma conduit — both may compose Tangible + Marked + Fixture. That difference is presentational only, so it belongs on the template that already identifies the object, as an optional icon; it does not justify a parallel taxonomy. Prose carries the genre. It always did.

6.4 Affordance resolution: why MML must not carry the verb list

The obvious design is to let the composer emit each noun's verbs. It fails on three counts, and the third is decisive.

  1. Bloat. A room description with twenty tagged nouns × a dozen verbs is a frame many times the size of its own prose.
  2. Staleness. A frame sits in scrollback forever. A door tagged unlock ten minutes ago is now a lie.
  3. Viewer-dependence. Verbs are gated by skill, permission and state, so the true menu is a function of (id, viewer, now). MML is a snapshot of then — it structurally cannot hold the answer.

The seam is composition versus state. A mixin set is stable — an object is Sealable and Lockable for its whole life. Its state is volatile — whether it is locked right now changes by the minute. So the split is principled rather than a compromise: put the stable half in the markup and resolve the volatile half live. A frame sitting in scrollback is still telling the truth when it says the door is Lockable; the only thing it cannot know is the position of the bolt.

So the tag and its mixin digest give an instant, offline-correct first guess, and the real menu resolves on demand:

1Compose: <thing id="#2d51" mx="Sealable,Lockable,Fixture">shed door</thing>
2Render: styled by tag; the mixin digest is already the affordance skeleton.
3Open: the radial appears immediately with the union of what those mixins afford — no round-trip, no spinner.
4In parallel: resolve live verbs for #4c1a against (viewer, now). One call, cached per id.
5Reconcile: unavailable verbs dim with their reason (“locked”, “needs Smithing 2”); newly available ones fill in.

This is the file-manager pattern — a right-click menu opens at once, and the slow entries populate into it. mudref: is already the plumbing for step 4; what is missing server-side is the resolver itself, returning each verb with an enabled flag and a reason.

Why the radial's slots are fixed. Categories hold position — perception north, manipulation east, social west, movement south — while their contents vary by kind and state. That is what lets muscle memory survive a menu whose verbs you have never seen before, and it is why the geometry must not reflow to fit the available verbs.

Menus are span-scope, so most of this is MML's business. One property is genuinely frame-scope, and belongs on the topic as a sixth facet: how long the affordances inside stay trustworthy.

Further questions this opens

  1. How wide is the mx digest? Emitting every composed mixin is honest but wordy on a dense room; emitting only those with an affords entry is compact and covers the menu. The pedagogical goal argues for the fuller list, since Chattel and Constructed teach something even though they afford nothing.
  2. Should fieldMeta.spoiler gate the mixin digest too? A creature's Combustible is a weakness, and the reveal model already runs on values — the composition may need the same treatment.
  3. Should the resolver return verbs the viewer cannot yet use, greyed with their requirement? Showing “needs Smithing 2” teaches the progression; hiding it keeps menus short.
